# 类天天富翁项目基础设施清单

## 1. 文档信息

- 项目代号：`fortune-board`
- 文档类型：前期基础设施清单
- 技术路线：`Cocos Creator 3.8 LTS + TypeScript`
- 目标平台：`iOS`
- 文档日期：`2026-03-28`

## 2. 结论摘要

当前项目处于前期调研和 MVP 规划阶段，优先目标是验证玩法，而不是立即搭建完整商业化手游后端。

因此基础设施建议分三阶段建设：

- 第一阶段：只上最小必要设施，保证能开发、能测试、能排错
- 第二阶段：补齐 MVP 测试所需的分析、配置和资源能力
- 第三阶段：在确认要做联网和商业化之后，再建设数据库和服务器

一句话结论：

- 当前阶段：`不必先上数据库`
- 当前阶段：`不必先上专用游戏服务器`
- 当前阶段最该有：`版本管理 + 文档 + 配置表 + 真机环境 + 崩溃监控 + 埋点 + 远程配置`

## 3. 阶段划分

### 3.1 第一阶段：原型与玩法验证期

目标：

- 跑通核心玩法
- 在 iPhone 真机上可玩
- 能快速迭代数值和规则
- 能看到崩溃和关键漏斗

此阶段不追求：

- 真正联网
- 完整账号体系
- 资产持久化
- 商业化后台

### 3.2 第二阶段：MVP 测试期

目标：

- 支持更稳定的测试与灰度
- 支持内容配置微调
- 支持简单排行或活动验证

### 3.3 第三阶段：联网与商业化扩展期

目标：

- 支持账号、房间、同步、排行、资产、运营系统
- 支持长期运行与版本迭代

## 4. 第一阶段必须有的基础设施

以下内容建议在开工前或开工第一周内准备完成。

### 4.1 代码与版本管理

- Git 仓库
- 分支规范
- `.gitignore`
- 版本号策略

目的：

- 保证代码、资源、配置和文档可追踪
- 为后续多人协作预留基础

建议：

- 主分支保持可运行
- 功能分支按模块拆分
- 配置表和代码一起提交，不要分离管理

### 4.2 文档体系

项目中建议至少保留以下文档：

- 需求文档
- 技术选型文档
- 基础设施清单
- 客户端架构设计文档
- 配置表规范
- 埋点事件字典

目的：

- 避免“只有脑中有规则，没有文档沉淀”
- 降低后续重构和多人协作成本

### 4.3 配置表体系

当前阶段非常重要，优先级高于数据库。

建议建立的配置表：

- 地图格子表
- 角色表
- 卡牌表
- 技能表
- 数值常量表
- AI 参数表

推荐形式：

- Google Sheets / Excel 维护
- 导出 `JSON`
- 项目内统一读取

原则：

- 所有规则尽量数据驱动
- 配置版本要可追踪
- 表结构先稳定，再扩字段

### 4.4 开发环境

必备：

- `Cocos Creator 3.8 LTS`
- `Node.js LTS`
- `Xcode`
- `Git`
- `VS Code`
- 至少 1 台可测试真机 iPhone

目的：

- 保证本地开发、构建和真机调试闭环

### 4.5 本地存档

当前阶段需要：

- 设置项存档
- 新手引导进度
- 本地测试配置
- 可选的对局恢复信息

建议：

- MVP 先使用本地 JSON 或本地存储
- 不急着做云存档

### 4.6 崩溃监控

建议第一版就接入：

- `Firebase Crashlytics`

原因：

- 真机问题和原生构建问题很难只靠本地日志排查
- 越早接入，越容易形成稳定的排障流程

### 4.7 埋点分析

建议第一版就接入：

- `Firebase Analytics`

当前阶段重点关注：

- 启动游戏
- 开始对局
- 完成引导
- 掷骰
- 买地
- 升级地产
- 使用卡牌
- 对局结束

原因：

- 玩法验证需要数据支撑，不能只靠主观感受

### 4.8 远程配置

建议 MVP 前期接入：

- `Firebase Remote Config`

适合远程控制的内容：

- 新手引导开关
- 数值实验参数
- 活动入口展示
- 调试和灰度标记

原因：

- 可以在不发版的前提下做小范围策略调整

## 5. 第一阶段暂时不需要的基础设施

当前不建议优先投入：

- 关系型数据库
- 专用游戏服务器
- 匹配服务
- 房间服务
- 聊天系统
- 公会系统
- 完整商城后端
- 完整运营后台

原因：

- 当前主目标是验证玩法，不是验证大型后端系统
- 小团队前期搭太多基础设施，通常会推迟“真正可玩版本”的到来

## 6. 第二阶段建议补充的基础设施

当项目进入 MVP 测试和内容验证阶段时，建议增加以下设施。

### 6.1 资源托管与 CDN

适用场景：

- 远程资源包
- 活动资源
- 后续 Asset Bundle 按需加载

建议：

- 使用对象存储 + CDN
- 将大厅资源、对局资源、活动资源拆开管理

### 6.2 构建与发布流程

建议增加：

- 命令行构建
- 固化打包参数
- 基础 CI

目标：

- 降低手工打包错误
- 提高多人协作时的一致性

### 6.3 测试与 QA 支撑

建议建立：

- 测试设备清单
- 冒烟测试 checklist
- 关键规则回归清单
- 核心日志导出方式

### 6.4 简单排行榜

如果只做 iOS 试水，可优先考虑：

- `Game Center Leaderboards`

适合场景：

- 单机成绩排行
- 局后得分榜

这样可以避免过早自建排行榜后端。

## 7. 第三阶段再建设的基础设施

当项目确定要做联网、账号和长期运营时，再上下面这些。

### 7.1 账号体系

适合需求：

- 多设备同步
- 玩家身份绑定
- 社交关系

可选方向：

- Apple 登录
- 第三方登录
- 自有账号体系

### 7.2 数据库

只有在出现以下需求时再上：

- 云存档
- 账号资料
- 活动配置后台
- 商城订单
- 发奖记录
- 资产流水
- 房间记录
- 对局记录

推荐思路：

- 轻后端阶段：`Postgres + Supabase`
- 联机游戏后端阶段：`Postgres + Nakama`

### 7.3 游戏服务器

只有在准备做以下功能时再上：

- 在线匹配
- 房间制对战
- 实时或准实时回合同步
- 断线重连
- 防作弊
- 服务端结算校验

推荐思路：

- 若只做轻量 API：普通后端服务即可
- 若做游戏房间和同步：优先考虑 `Nakama`

### 7.4 运维设施

进入联网阶段后补齐：

- 服务监控
- 日志聚合
- 告警
- 任务队列
- 管理后台
- 数据备份

## 9. 基础设施决策原则

### 9.1 先验证玩法，再验证后端

对这个项目来说，最贵的失败不是“后端不够强”，而是“玩法本身不好玩”。

### 9.2 先选最小闭环，不选最大方案

每新增一项基础设施，都会增加：

- 接入成本
- 学习成本
- 维护成本
- 排障成本

### 9.3 数据驱动优先于数据库驱动

在玩法原型期：

- 配置表比数据库更重要
- 可复现的对局日志比复杂后台更重要

### 9.4 服务端只在有明确价值时引入

服务端最适合解决：

- 多端同步
- 联机状态
- 资产可信度
- 运营配置与记录

在这些需求出现之前，不建议提前建设。

## 10. 建议的近期动作

建议按以下顺序推进：

1. 完成 Cocos Creator 项目初始化
2. 建立配置表和导出流程
3. 跑通 iOS 真机构建
4. 接入 Crashlytics、Analytics、Remote Config
5. 完成一局可玩的本地 MVP
6. 再评估是否需要数据库或服务器
