## 1.1 文档使用原则

## 2. 结论摘要

本项目建议使用 `Cocos Creator 3.8 LTS + TypeScript` 作为客户端主技术栈，优先交付一款 iOS 平台的类天天富翁游戏 MVP。

选择 Cocos Creator 的核心原因：

- 更适合小团队快速制作 `2D/2.5D` 棋盘休闲游戏
- 对前端/脚本开发者更友好，`TypeScript` 上手成本较低
- UI、动画、资源组织、跨平台发布链路清晰
- 官方手册明确支持原生 iOS 发布、命令行构建、Asset Bundle、原生桥接
- 如果后续扩展至小游戏、Web 或 Android，复用空间更大

不选择 Unity 作为当前主方案的原因：

- 当前目标是尽快做出 iOS 可玩 MVP，而不是直接铺大型商业化工业链路
- 对小团队而言，Unity 的工程复杂度和学习负担更高
- 对本项目核心题材来说，Cocos Creator 在表现力上足以覆盖 MVP 需求

## 3. 项目技术目标

### 3.1 必须满足

- 可发布 iOS 原生包
- 支持高效开发 2D/轻 2.5D 棋盘玩法
- 支持数据驱动的规则、卡牌、地图和角色配置
- 支持资源分包和后续热更新思路
- 支持接入原生 iOS 能力

### 3.2 应尽量满足

- 代码结构清晰，适合持续扩展
- 小团队维护成本低
- 构建、打包、真机调试流程明确
- 保留未来扩展到 Android 和小游戏的可能性

## 4. 候选方案对比

### 4.1 Cocos Creator

优点：

- `TypeScript/JavaScript` 脚本开发体验友好
- 更轻量，适合休闲和轻中度游戏
- UI 工作流自然，适合信息密度较高的棋盘类产品
- 资源组织与 Asset Bundle 适合后续做内容分包
- 官方支持 iOS、Android、Web、小游戏多端发布

缺点：

- 大型商业手游常见现成插件和资产生态不如 Unity 丰富
- 更复杂的高端渲染、特效、3D 管线通常不如 Unity 成熟
- 团队规模做大后，规范和基础设施需要更主动建设

适配度判断：

- 本项目匹配度：`高`

### 4.2 Unity

优点：

- 工业化工具链更成熟
- 商业手游生态、插件、现成方案非常丰富
- 更适合复杂 3D、重特效、多人协作和长期商业化扩展

缺点：

- 工程复杂度更高
- 小团队原型期开发负担更重
- 对当前题材的 MVP 优势没有大到足以抵消成本

适配度判断：

- 本项目匹配度：`中高`

### 4.3 原生 iOS

优点：

- 平台整合最直接
- 包体和系统协同控制更细

缺点：

- 游戏编辑器和内容工作流弱
- 对地图、资源、动画、配置和跨平台扩展不友好
- 整体产研效率不如专用游戏引擎

适配度判断：

- 本项目匹配度：`中`

## 6. 建议的技术原则与候选架构

### 6.1 分层设计

实现时可优先按职责分层，而不是先追求复杂框架。当前更重要的是把规则、表现和基础能力拆开，避免早期互相污染。

可参考以下分层思路：

- `Core`
  - 核心规则
  - 回合状态机
  - 结算逻辑
  - 地图和格子逻辑
- `Gameplay`
  - 角色系统
  - 地产系统
  - 卡牌系统
  - 技能系统
  - AI 系统
- `Presentation`
  - 场景
  - UI
  - 动画
  - 音效
  - 特效
- `Infrastructure`
  - 资源加载
  - 存档
  - 埋点
  - 崩溃上报
  - 配置读取
  - 原生桥接

### 6.2 候选目录结构示意

以下仅作为工程初始化时的候选示意，不代表必须一次性按此结构落地。实际目录应以首个可玩版本最顺手、最易维护为准。

```text
assets/
  scenes/
  prefabs/
  ui/
  art/
  audio/
  effects/
  bundles/
  scripts/
    core/
    gameplay/
    systems/
    ui/
    data/
    ai/
    bridge/
    utils/
config/
docs/
native/
tools/
```

### 6.3 核心设计原则

- 规则层与表现层解耦
- 数据配置与逻辑代码解耦
- UI 和局内逻辑事件解耦
- 所有关键逻辑必须可记录、可复现、可测试

## 7. Cocos Creator 能力映射

### 7.1 为什么适合本项目

根据 Cocos Creator 3.8 官方手册，项目最相关的能力包括：

- 脚本系统支持 `TypeScript/JavaScript`
- 支持 2D、UI、动画、音频、资源管理
- 支持原生平台发布到 iOS
- 支持原生二次开发和 `JavaScript <-> Objective-C` 通信
- 支持 `Asset Bundle` 做资源模块化和按需加载
- 支持命令行发布，适合后续接 CI

### 7.2 在本项目中的使用方式

- 场景系统：大厅、角色选择、对局、结算
- 预制体：格子、角色棋子、UI 面板、弹窗
- Tween/Animation：角色移动、金币变化、地产升级反馈
- Asset Bundle：大厅资源、对局资源、活动资源拆分
- Native Bridge：后续接支付、登录、统计、推送

## 8. 实现时优先验证的技术方向

### 8.1 渲染与表现

建议走 `2D/轻 2.5D` 路线：

- 地图以 2D 棋盘为主
- 角色和建筑可做分层 pseudo-3D 效果
- 重点投入在反馈动效，而不是复杂实时光照

这样更符合：

- 棋盘游戏的阅读性
- iPhone 中端机型性能稳定
- 小团队美术与程序产能

### 8.2 UI 技术方案

当前建议优先使用 Cocos 原生 UI 系统，先验证是否足以支撑 MVP：

- 主页和大厅使用场景内 Canvas 组织
- 对局主界面采用固定 HUD + 弹窗层
- 将局内面板拆成独立 prefab
- UI 动画统一使用 Tween 和状态控制

原则：

- 主 HUD 轻量
- 二级信息用弹层
- 不让 UI 遮挡棋盘的关键反馈

### 8.3 数据驱动方案

建议优先把高频改动内容做成配置，但不要求在第一天就把所有内容彻底表格化。可优先考虑以下对象：

- 角色表
- 地图格子表
- 卡牌表
- 技能表
- 数值常量表
- AI 参数表

运行时可以先有统一配置入口，具体命名和实现方式在工程落地时再定。

优点：

- 平衡性调整成本低
- 后续扩地图和活动更容易
- 测试和排错更方便

### 8.4 状态机方案

核心对局应具备明确的阶段流转。实现时可以采用状态机，也可以采用其他同样清晰、可测试的流程组织方式。若使用状态机，可参考以下阶段：

- `GameInit`
- `TurnStart`
- `RollDice`
- `MovePiece`
- `ResolveTile`
- `UseCardOptional`
- `TurnEnd`
- `GameOver`

不要把回合逻辑散落在零碎 UI 回调里，否则很快会失控。

### 8.5 AI 方案

MVP AI 不追求智能博弈，采用规则驱动：

- 有钱优先买关键地产
- 收益高时优先升级
- 遇到威胁时优先使用保命或位移卡
- 回合开始和事件结算后做简单决策

后续如果需要再升级成评分模型或搜索模型。

### 8.6 存档方案

MVP 采用本地存档：

- 设置项
- 新手引导进度
- 最近一次配置版本
- 可选的中断对局恢复

实现上可先用简单、稳定的本地方案，具体落地形式在工程搭建时再确认。

### 8.7 日志与调试

建议从第一版就做：

- 对局事件日志
- 关键结算日志
- 状态机切换日志
- 配置版本日志

这样未来排查“规则错了”“AI 卡住了”“回合没结束”会快很多。

## 9. iOS 发布与原生集成

### 9.1 iOS 发布

Cocos Creator 官方手册提供了 iOS 原生发布能力和构建选项。项目中应使用：

- Xcode 作为最终打包和签名工具
- Apple Developer 证书和描述文件
- 真机调试验证输入、音频、性能和内存表现

### 9.2 原生能力接入边界

MVP 阶段建议把原生集成控制在有限范围内，只在确实需要时再接：

- 崩溃上报 SDK
- 埋点 SDK
- 登录能力
- 支付能力
- 推送能力

原则上应有统一桥接边界，不让业务层直接分散调用原生接口；具体服务命名和封装方式在实现时确定。

### 9.3 Web 界面策略

如果后续采用原生 iOS + Web 页面混合方案，可参考以下边界：

- 游戏主循环和主界面仍由 Cocos 承担
- Web 只负责活动页、公告页、帮助页
- 购买和资产相关闭环保留在原生/游戏层

## 10. 资源与热更新策略

### 10.1 资源拆分原则

如果后续需要做资源拆分，可优先按功能拆包。以下命名仅作示意：

- `base`：公共 UI、基础音效、常用图集
- `battle`：棋盘场景、角色棋子、局内特效
- `lobby`：大厅和非对局界面资源
- `event`：活动资源预留

### 10.2 Asset Bundle 使用策略

根据官方文档，Asset Bundle 适合按需加载和降低首包/首屏压力。当前方向建议如下：

- 基础资源内置
- 对局资源单独 bundle
- 活动资源独立 bundle
- 后续如需扩展，再设计远程资源更新

### 10.3 热更新判断

MVP 阶段不建议一开始就做完整热更新系统。

建议顺序：

1. 先做配置远程下发
2. 再做资源 bundle 更新
3. 最后再评估完整热更新机制是否值得

原因：

- iOS 审核边界要谨慎
- 小团队前期更该优先保证玩法完成度

## 11. 构建与工程化

### 11.1 构建方式

中后期建议同时支持：

- 编辑器内本地构建
- 命令行构建

命令行构建的目的：

- 后续接 CI
- 固化构建参数
- 降低人工打包失误

### 11.2 环境建议

- Cocos Creator `3.8 LTS`
- Node.js `LTS`
- Xcode 最新稳定版
- Git
- VS Code

### 11.3 开发规范

- `TypeScript strict` 尽量开启
- ESLint + Prettier
- 配置文件命名统一
- prefab 和脚本命名统一
- 核心逻辑模块补单元测试或规则测试

## 12. 第三方依赖建议

MVP 阶段建议尽量少依赖第三方插件，避免后期维护成本上升。

建议保留的类别：

- 埋点与崩溃监控
- Spine 或骨骼动画运行库
- 必要的原生 SDK 桥接

不建议早期引入：

- 大而全的框架型插件
- 重度依赖编辑器扩展的方案
- 与本项目玩法无关的通用系统库

## 13. 风险分析

### 13.1 技术风险

- 规则和表现耦合后，后续改一处影响全局
- 热更新如果过早引入，会显著增加工程复杂度
- 原生桥接如果分散调用，会让项目难以维护

### 13.2 性能风险

- 过多动态创建节点导致卡顿
- UI 层级过深导致重绘压力变大
- 动画、特效和音效并发过多引起掉帧

### 13.3 管理风险

- 配置表和代码版本不同步
- 美术资源命名混乱
- prefab 依赖关系不清
